# 上下文银行 · Skills、经验与工作流分享站 PRD

版本：0.3 · 2026-10-18 · 状态：评审稿与离线界面原型

## 1. 定位与命名

品牌名建议：**上下文银行**。副标题：**Skills · 经验 · 工作流**。传播语：**好方法，拿来就用。** 产品解释：每个人都能分享AI工作方法，个人上下文保留在自己管理的工作目录。

“上下文银行”延续群内概念，品牌可容纳经验、流程与技能；名称本身可能让人联想到托管个人记忆，所以页面始终展示三类内容和“个人上下文，自己管理”的说明。“Skills银行”更直观地指向技能分发，但对文章和工作流的包容性较弱，适合作为备选名。“AI工作实践库”只作为产品品类说明，不作品牌名。命名为建议，未做商标或域名可用性调查。

## 2. 要解决的问题与首版任务

好方法散落在同事聊天、文章和代码仓库，新同事不容易找到可直接照用的版本。擅长AI的人缺少低成本分享入口，培训结束后缺少可重复使用的操作材料。

首版任务：任何访问者都能搜索和阅读公开实践，找到适合当前任务的方法；按详情页复制步骤、下载模板或使用作者提供的安装说明；将方法用于自己管理的工作目录；有改进后自行整理、脱敏并提交新的实践。

核心闭环：**发现 → 取用 → 在自己的目录完成任务 → 整理可分享方法 → 投稿 → 更多人复用**。

## 3. 产品边界

平台存储主动投稿且获准公开的Skills说明、经验文章、工作流步骤、示例、作者与来源信息。投稿主体确认有权公开，团队内部资料需遵循所在组织的公开规则。

个人聊天、客户材料、项目进度、个人偏好与原始工作成果由本人保存在自己的目录或个人知识库。平台无扫描目录、自动读取聊天、托管个人记忆或跨平台同步功能。网页在本地生成用户选定的方法文件或索引申请；正式写入通过GitHub PR完成。

任何人可浏览、取用、生成投稿文件，无需本站注册登录。人和获授权的Agent均可通过公开仓库PR投稿或申请索引。GitHub写入需要GitHub身份或受授权凭据，免站内登录不等于匿名写入。源码、内容规范、公共示例与贡献流程计划开源；本次仅更新设计文件，尚未创建或发布公开仓库。

## 4. 内容模型：三种类型，同一套详情结构

|类型|用户得到什么|主要动作|最少内容|
|---|---|---|---|
|Skill|可让支持该技能格式的Agent执行的方法包|查看来源、复制作者安装命令或下载|公开仓库、技能路径、版本、工具兼容性、许可、所需权限与使用示例|
|经验|解决问题的思路和可复制的提示词|阅读、复制提示词、下载MD|问题、适用条件、具体做法、示例、限制、作者|
|工作流|多个步骤组成的任务操作说明|复制完整步骤、下载模板|输入、步骤、输出、人工检查点、工具依赖、示例|

三种类型可互相关联：经验解释思路，工作流串起步骤，Skill承接可执行部分。首版不要求作者同时提交三类内容。详情页使用同一框架，让非技术同事无需理解技术分类也能开始。

## 5. 界面与在哪里用

主入口为一个可分享的网站，桌面和手机可浏览。首页采用技能目录常见的紧凑列表：搜索框、类型与场景筛选、精选/最新排序、标题、简介、作者、更新日期。借鉴skills.sh的“搜索发现＋详情取用”路径，视觉与内容为本方案原创。

首版三个核心页面：

1. **发现页**：一句话说明价值，直接搜任务；按Skills/经验/工作流及写报告、表格分析、会议、研发等场景筛选。无搜索结果时提供清除筛选和投稿入口。
2. **详情页**：先展示“解决什么、适合谁、怎样开始”，再给步骤、样例、来源、版本、许可、已验证工具和限制。Skill可复制安装说明；经验可复制提示词；工作流可下载操作模板。
3. **分享页**：三个入口——收录已有公开仓库、网页生成Markdown后通过GitHub投稿、让Agent准备PR。无需本站账号；展示生成文件、GitHub步骤与状态解释，不把本地生成误称为已提交。没有仓库的同事可向公共内容仓库贡献文件。正式仓库配置前不显示可执行的伪地址。

附属入门页以三个动作讲清怎么用：选方法 → 带到现有AI → 保存在自己的目录。页脚始终说明个人上下文由本人管理。

工具接入不依赖统一入口：支持本地文件访问的Agent按用户授权读取目录；浏览器AI可使用复制文本或文件上传，支持情况逐工具标注。不宣称所有Agent通用；没有完成验证的标注“未验证”。

## 6. 普通同事的使用路径

例：想快速写好周报。打开网站搜索“周报” → 读详情和虚构示例 → 复制提示词及步骤 → 在自己使用的AI中粘贴，按组织规则提供材料 → 检查结果 → 将产物和下一步保存到自己的目录。

建议的个人目录模板：

```text
我的工作/
├── 工作说明.md           # 偏好、约束、工具使用说明
├── 项目A/
│   ├── 背景.md
│   ├── 当前进展.md
│   ├── 资料/
│   └── 产出/
└── 可分享的方法/         # 本人整理、脱敏后再主动投稿
```

目录管理由本人决定，平台仅提供空白模板与实践指引。文件夹位置、同步盘、备份以及对AI工具的授权由用户自行选择；下载模板不会触发目录扫描或上传。

## 7. 公开仓库驱动的发布与维护

### 7.1 三条投稿路径

- **已有仓库**：作者公开仓库放方法文件及元数据，通过索引仓库PR提交repository、path和ref。系统只读取声明路径与依赖的已声明资源，不遍历个人目录。发布索引固定到commit，保留原作者、来源与许可；更新时重新检查。
- **网页投稿**：任何人填经验/工作流，网页本地生成Markdown并下载。用户前往公共内容仓库，用GitHub网页上传并发起PR；无需自建仓库。正式版可在文件较小时预填GitHub新文件页，超长正文使用下载/上传路径。网站不持有GitHub写入凭据。
- **Agent投稿**：获用户授权的Agent按CONTRIBUTING.md和Schema生成文件，通过既有GitHub身份fork、提交和发起PR。提供可复制的任务指令和贡献指南。Agent没有匿名直写main的特殊权限。

### 7.2 提交、收录、精选的区别

提交成功以GitHub PR URL为准；本地文件生成不等于提交。自动检查通过不等于已收录；收录以索引/内容PR合并并成功构建后实际详情页可访问为准。编辑精选和任务验证单独标注，不由发布者或安装次数自动获得。

状态：本地草稿 → PR已提交 → 自动检查 → 首次作者人工审核 / 可信作者快速通道 → 已合并待构建 → 已收录。检查失败、修改请求、来源不可达、构建失败各展示原因；详情页只读最后成功构建的发布版本。

首次作者经过简短审核。可信作者由维护者明确授予，只有修改限定内容目录、来源与许可不变且检查全通过的低风险PR可自动合并。涉及脚本、执行权限、外链依赖、许可变更或工作流配置的提交始终转人工。外部投稿检查在无写权限、无密钥环境运行，不执行投稿脚本，不用带特权的工作流检出不可信PR代码。

PR本身即可能公开：提交到公共仓库前就应完成内容选择、脱敏与公开授权。平台检查不是防泄漏保证。平台只展示方法，个人项目、客户材料与聊天不进入投稿。

更新沿用PR流程。撤下用索引移除或维护者紧急下架；Git历史与第三方副本不能保证删除。来源失效显示不可用标识，禁止伪造安装或下载。站点不直接托管作者的个人工作目录。

作者声明的兼容性与平台验证分开。后者必须含工具版本、验证日期、任务与证据；首版不展示虚构热度、安装量或收益。

## 9. 数据、仓库与技术建议

公开仓库规划为网站源码、内容/索引、贡献文档三部分，可在首版同一个仓库分目录维护。最终owner/repo由用户指定；当前不假定任何仓库已存在，也不把带内部材料的现有仓库改成公开。

```text
site/                      # 网站源码
content/notes/<slug>.md     # 经验
content/workflows/<slug>.md # 工作流
registry/<slug>.yaml       # 外部Skill/方法索引
schemas/                   # 内容与索引约束
CONTRIBUTING.md             # 人和Agent统一贡献规范
.github/                   # 模板、检查与发布流程
```

统一元数据包括schema_version、id、type（skill/note/workflow）、title、summary、scenarios、author、license、compatibility与来源。正文包含输入、步骤、示例、限制。外部索引补repository、path、ref、resolved_commit；仓库URL白名单、大小限制、解析超时与内容清洗由构建端执行。仅接受公开来源，不索取私人仓库凭据。

初期：GitHub作为内容与贡献事实来源 → 隔离环境检查Schema、重复项、链接、许可完整性与明显敏感内容 → 合并后构建静态站 → 发布目录与全文索引。前端搜索本地索引。网站无需本站账号系统、数据库投稿API或GitHub Token输入框。访问增长后再升级搜索服务。

面向Agent提供受控纯文本贡献指南、Schema与已收录目录JSON。正文对人是操作说明，对Agent是待用户授权采用的内容，不作为提升权限的系统指令。贡献时记录提交者与Agent协助标识；作者归属来自声明并与提交主体关联，不能任意冒名。

不另造技能安装器：符合现有Skill格式的内容保留作者正式安装方式。经验与工作流用轻量Markdown。网站代码许可与内容许可分开记录，索引他人仓库不改变原许可。

### 9.1 建议发布时效与故障处理

网页生成文件本地即时完成。首次投稿人工审核建议1个工作日内响应；可信投稿在检查通过后触发快速通道，目标10分钟内可见。时效为待验证运营目标，受GitHub与发布服务影响。失败保留PR与构建日志，站点继续使用上一成功版本，修复后重建。

## 10. 传播设计：让同事第一次就用起来

传播语：**好方法，拿来就用。** 解释语：**分享Skills、经验和工作流；个人上下文，自己管理。**

传播落点为具体实践详情页。群消息、文章、培训课件都链接到能马上照做的一条实践，首页作为总目录。

首轮准备6条完整实践：2个Skills、2篇经验、2条工作流，覆盖报告、表格和研发；每条有虚构输入、输出样例、适用工具和限制。只有真实完成验证的内容才能称为“已验证”。

同事首次使用3分钟：搜索一个任务 → 复制一个方法或下载模板 → 在自己已有的AI中试做。非技术同事默认走复制路径，熟悉命令行的同事可按详情使用安装路径。

内部教练用10分钟带一次真实任务：选方法、示例演练、检查结果、保存到本人目录；下一周收集失败情况，更新原方法。作者分享卡包含一句痛点、一张产物示例、详情链接和适用工具，避免空泛推荐。

投稿引导：『把你已经用顺手的一招写下来：解决什么问题、怎么做、给个脱敏示例。没有代码也可以分享。』收录后提供可复制的分享文案和详情链接，由作者主动传播。宣传“免站内注册，人和Agent都能投稿”；写入GitHub需要对应身份。

## 11. 试点与成功标准

建议两周可用性试点，5名使用者、2名分享者。第一周完成6条可用内容与目录、详情、本地生成、PR检查与构建流程；第二周完成至少15次任务尝试。此排期以人员和基础设施已就绪为前提。

建议目标：首次使用者≥80%能在3分钟内找到并复制适合的方法；至少70%的尝试经用户确认完成预期任务；2名分享者（至少1名通过Agent）都能在10分钟内生成完整文件并发起PR；个人上下文自动上传次数为0。记录搜索无结果、适配失败和步骤不清等原因，样本量与耗时一同报告。

衡量从“找方法到完成任务”的效果；复制、下载和安装次数只作为行为数据。平台运营能查看公开实践与投稿状态，不采集个人任务正文。
